The root cause below is still open. Asking the assistant to book two slots in one message ("add appointments at 11:00am and 2:00pm today, 1 hour each") shows a card for the first, and the second is silently dropped once the first is booked. The assistant says it will show a card for each, so the visitor isn't told the second never appeared. Cause (your diagnosis, checked in the code, not reproduced): "Pay $1 deposit" goes to `/checkout`, and `stripe.confirmPayment` there has a `return_url` (`src/pages/Checkout.tsx`), a full-page redirect to Stripe and back to `/payment/success`. The chat's cards live only in React state (`widgets` on the reply) and the history `GET` returns text only, so after the redirect the second card is gone. It is the same root cause as the "cards are not restored on history reload" gap above. Fix: have the history endpoint return each turn's UI events (`replyFromStoredTurn` already rebuilds them from stored rows) and render them on reload; a restored card for a slot that is already booked must then show as booked, not offer to pay again (compare with the booked appointments, or re-check availability). The booking is also pending in `sessionStorage` as a single `pending_appointment`, which is fine for one card at a time. Needs a test (e2e: two `slot.proposed` events, pay the first, come back, the second card is still there). If this is fixed, remove the one-at-a-time rule from `VISITOR_PROMPT`.
